# GPC Order Block — interchange format v1

A single block of text that carries everything needed to build a
`.gconfiguration`: the customer, the addresses, the contact, and the
configuration itself. Generated by another system — an Odoo sales order, say —
copied once, and pasted into gpc-viewer.

The point is that nobody retypes an address, and nobody hand-picks forty SAP
codes out of a catalog that has 3,827 articles in it.

## Envelope

```
-----BEGIN GPC ORDER-----
eyJncGNPcmRlciI6MSwic291cmNlIjp7InN5c3RlbSI6Im9kb28i…
-----END GPC ORDER-----
```

The body is **base64** of the UTF-8 JSON document below. Line breaks inside the
body are ignored, so the block survives e-mail, chat and PDF copy-paste, which
raw JSON does not — a wrapped quote mark or a smart-quoted `"` breaks a JSON
paste and is invisible to the person doing it.

gpc-viewer also accepts **bare JSON**, with or without the envelope, so a
generator can be debugged by eye. Emit the envelope in production.

## Document

Every field is optional except `gpcOrder`. Anything absent is left as the blank
order has it; anything unrecognised is reported and ignored, so a newer
generator never breaks an older viewer.

## Items

Three kinds. Each is matched against the open catalog, and anything that cannot
be matched is **reported, not guessed** — a paste never silently drops a line.

### `article` — a catalogue product

```jsonc
{ "type": "article", "sapNr": "000250-0004-933", "amount": 1 }
{ "type": "article", "name": "Calibration Panel CPA30/210", "amount": 2 }
```

`sapNr` is the **ZEISS** SAP number — the one the GPC catalog keys articles on,
not an internal SKU. In Odoo it is the vendor product code on the ZEISS vendor
line (`product.supplierinfo.product_code`, the Purchase tab), so a generator
reads it from there rather than from the product's own reference.

It is preferred over the name because it survives a rename, and catalogs do
rename articles between releases. `name` is the catalog `LongName` and is used
when the SAP number is absent or matches nothing.

Give both. A SAP number that matches exactly one article is used on its own;
one that matches several is settled by the name, and refused if no name was
given. That case is real — PDB290 has SAP numbers shared by more than one
article — and it is also why the vendor rows are dated: ZEISS numbers and
prices move between PDB releases, so a generator should read the row valid for
the order and set `catalog` to the release it belongs to.

`amount` defaults to 1.

### `license` — a software licence

```jsonc
{
  "type": "license",
  "name": "2026 Sensor Driver ARAMIS",
  "userEmail": "licensing@trilion.com",
  "userName": "Trilion Licensing"
}
```

A licence is an option inside a dependent list, so the viewer finds the list
that offers it and adds that line with the option selected. `sapNr` is accepted
but licences are identified by name in the catalog.

### `sma` — a maintenance agreement

One entry per **dongle**. Several agreements on one dongle go in its `articles`
array, not in separate entries — that is how GPC groups them.

```jsonc
{
  "type": "sma",
  "dongleId": "3-7619774",
  "endOldContract": "2026-07",        // YYYY-MM or YYYY-MM-DD
  "startNewContract": "2026-10",      // optional; omit to start the next month
  "months": 12,                        // optional; 12 or more
  "articles": [
    "EXT SMA for Sensor Driver ARAMIS",
    "EXT SMA for ZEISS CORRELATE - Pro Line"
  ],
  "licenseUserEmail": "licensing@trilion.com",
  "licenseUserName": "Trilion Licensing"
}
```

**Terms run in whole months.** A start is snapped to the first of its month and
an end to the last day of one; there is no part-month agreement, and the
pricing counts whole months regardless. Sending `2026-07-14` as
`endOldContract` is accepted and means `2026-07-31`.

A `startNewContract` later than the month after `endOldContract` leaves a
deliberate gap. The lapsed months are not charged.

## What the viewer does with it

1. Decodes and validates. A malformed block is refused with the reason; nothing
   is applied by halves.
2. Warns if `catalog` names a product database other than the open one, and
   offers to switch, because prices and SAP numbers move between catalogs.
3. Shows a preview: every field that will change, every item that resolved, and
   every item that did not.
4. Applies on confirmation, as one edit.

## Compatibility

`gpcOrder` is the format version. A viewer refuses a version it does not know
rather than guessing at it. Within version 1, new optional fields may be added:
generators must not assume a field they emit is understood, and viewers must
ignore fields they do not recognise.
